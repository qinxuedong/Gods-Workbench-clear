# Phase 12 PDF 修复方案｜独立设计审核

审核对象：`PHASE-12-PDF-REPAIR-DESIGN.md`；仅方案审核，不是实现验收，不修改生产代码。

## 结论

**有条件通过，可按此方向实施；下列四项最小补充须作为 Required 验收条件。**标准库自研 Type0/CID、分页、ToUnicode、UTF-8原文附件的方向可行，不需要新增运行依赖或仓库二进制。非嵌入字体不承诺任意阅读器一致的限制已经写清；当前Chrome与PyMuPDF中文可读仍是必须实测的门禁，附件不能替代正文可读。

### D1｜字体编码与宽度必须明确绑定

- 固定 Type0 + CIDFontType0、STSong字体名、Adobe/GB1的CIDSystemInfo、相容的Supplement/PDF版本和必需FontDescriptor；不要只写一个字体名字就假定所有阅读器能够渲染。
- 正文字符码使用UTF-16BE；ToUnicode将**实际发出的字符码**映射到Unicode，不把CID误当Unicode。采用明确的codespace；不能拆开UTF-16代理对。
- 明确支持字符集合，未承诺的字符先转为可读Unicode转义，再进行换行。不能把“可编码成GB18030”或“处于汉字区间”当成实际字形覆盖证明。
- “安全字符宽度”必须与字体的DW/W或定位指令一致。尤其DW=1000时，不能未经W配置便假定ASCII只占半个字号；W表索引是CID，不是Unicode码点。先转义再计算宽度，避免Emoji长转义越界。

### D2｜无损边界、资源上限和附件结构写死

- `source.txt`定义为**送入生成器的原始全文的UTF-8字节**，在换行规范化、转义、分页之前保留；各路由组装原文的规则明确。附件不能是已经问号替换/截断的正文副本。
- 附件作为文档Names/EmbeddedFiles→Filespec→EF→EmbeddedFile的真实可提取对象；固定安全文件名，正确字节Length/xref；不通过外部路径、JS、Launch/OpenAction自动执行附件。
- 限制至少包含输入UTF-8字节数、转换后显示字符/行数、页数（及ToUnicode映射规模）。超限必须在HTTP200/输出流开始前返回标准错误。非法Unicode如孤立代理项应400/422，不得500或replace丢失。
- PDF正文允许显式转义，附件要求字节完全一致；附件抽取能力与阅读器是否显示附件UI分开声明。无需承诺Chrome一定提供附件面板。

### D3｜分页与导出计数不能只测“非白”

- A4纵向/48边距/11字号/17行距/42行的组合可作为保守版式，但按**换行后的物理行**分页；标题、空行、页码占用须计入。
- 1/41/100条之外补正好42/43物理行、超长ASCII/汉字/混排、连续Unicode转义；断言首项和末项可见、页数与实际排版一致，全部文字bbox在安全纸面内。“像素非白”不能证明内容完整。
- 注册表对未知ID明确选择全请求404，或明确跳过并给出真实exported/skipped数量；重复ID去重规则同样固定。三个输出面必须从同一份已读取快照计算正文/附件/计数，不能边输出边读取变化中的状态。

### D4｜门禁覆盖及通过措辞

- 三个HTTP面均以中文合法实体测试：200、RFC5987文件名、PDF解析、中文文本提取、附件精确UTF-8、末项和分页；401/403不回退。全套测试不访问商业Provider。
- 当前Chrome与PyMuPDF均实际打开/渲染中文正文；第一页与尾页（含跨页长行）均目视。至少包含常用简体汉字、中文标点、ASCII、括号/反斜杠，以及明确转义的Emoji/罕见字。
- 若预定义非嵌入字体在任一目标阅读器失败，R9仍未完成；不要靠ToUnicode提取正确或附件正确掩盖不可读正文。此时保留失败证据，再评审现有白名单字体的嵌入方案，不私增依赖。
